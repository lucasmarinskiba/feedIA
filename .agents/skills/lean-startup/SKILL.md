# SKILL: The Lean Startup — Validación Rápida e Iteración

## Source: Eric Ries — "The Lean Startup" (2011)

---

## PRINCIPIO CENTRAL

"Startup success can be engineered by following the right process, which means it can be learned, which means it can be taught."

El fracaso de la mayoría de startups no es falta de visión, talento, o esfuerzo — es falta de proceso. El Lean Startup provee ese proceso para condiciones de extrema incertidumbre.

**Definición de startup**: "A human institution designed to create a new product or service under conditions of extreme uncertainty."

No importa el tamaño de la empresa, la industria, o si está en un garaje o dentro de una multinacional. Si opera bajo incertidumbre extrema sobre quién es el cliente y qué debe ser el producto → es una startup y necesita este proceso.

---

## EL LOOP CENTRAL — BUILD-MEASURE-LEARN

```
         IDEAS
           ↓
        BUILD  ←←←←←←←←←←←←←←←
           ↓                     ↑
        PRODUCT                  ↑
           ↓                     ↑
        MEASURE                  ↑
           ↓                     ↑
         DATA                    ↑
           ↓                     ↑
         LEARN                   ↑
           ↓                     ↑
    PIVOT o PERSEVERE →→→→→→→→→→↑
```

**El objetivo no es completar el loop — es completarlo lo más rápido posible.**

Cada ciclo completo = una hipótesis validada o refutada.

---

## LOS 5 PRINCIPIOS DEL LEAN STARTUP

1. **Entrepreneurs are everywhere**: Entrepreneur = cualquier persona creando algo nuevo bajo incertidumbre extrema. No importa si está en un garaje, en una corporación, en una ONG, o en el gobierno.

2. **Entrepreneurship is management**: Una startup es una institución, no solo un producto. Requiere gestión específica para condiciones de incertidumbre extrema. Los métodos de gestión tradicional no están diseñados para esto.

3. **Validated Learning**: El progreso no se mide en features lanzados, en código escrito, ni en dinero gastado. Se mide en aprendizaje validado — hipótesis sobre el negocio probadas con datos reales.

4. **Build-Measure-Learn**: La actividad fundamental = convertir ideas en productos, medir respuesta de clientes, decidir si pivotar o perseverar. Toda la organización debe optimizar para acelerar este loop.

5. **Innovation Accounting**: Para mejorar outcomes, necesitamos métricas específicas para startups: milestones de aprendizaje, not de ejecución. Accionables, no vanity metrics.

## MVP — MINIMUM VIABLE PRODUCT

"That version of a new product which allows a team to collect the maximum amount of validated learning about customers with the least effort."

**El MVP no es el producto más pequeño posible — es el experimento más pequeño posible que prueba la hipótesis más importante.**

### Tipos de MVP

| Tipo                | Descripción                                                | Ejemplo                                                                                 |
| ------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Landing Page MVP    | Medir intención antes de construir                         | Dropbox: video explicativo que captura emails antes de que el producto existiera        |
| Concierge MVP       | Hacer manualmente lo que el producto haría automáticamente | Airbnb: fotografías profesionales realizadas por el equipo antes de tener el sistema    |
| Wizard of Oz        | Fingir automatización que se hace a mano                   | Zappos: comprar zapatos en tiendas locales y venderlos online antes de tener inventario |
| Minimum Feature Set | Solo la feature más crítica                                | Facebook: solo perfiles y conexiones — sin noticias, fotos, ni grupos                   |
| Smoke Test          | Medir si alguien pagaría antes de construir                | Botón "Comprar" que lleva a "Próximamente" — medir clicks = intención de compra         |

**Regla de oro del MVP**: Si te da vergüenza la primera versión que lanzas, la lanzaste demasiado tarde.

## VALIDATED LEARNING vs VANITY METRICS

### Vanity Metrics (métricas que se ven bien pero no informan decisiones)

- Total de usuarios registrados
- Total de descargas
- Total de page views
- Ingresos brutos históricos

**El problema**: Solo van hacia arriba. No importa qué hagas, estas métricas "mejoran". No te dicen si el negocio está funcionando o si debes cambiar de dirección.

### Actionable Metrics (métricas que informan decisiones)

**Cohort Analysis** — Comparar grupos de usuarios por período de adquisición:

- "El cohorte de enero retuvo 40% al mes 3"
- "El cohorte de febrero (con el nuevo onboarding) retuvo 65% al mes 3"
- → El nuevo onboarding mejora retención

**Conversion Funnels** — Medir tasas de conversión en cada paso:

- 1,000 visitas → 200 trials (20%) → 50 pagos (5% total)
- Problema: ¿Dónde se pierde? → Diagnóstico preciso vs "las ventas bajaron"

**Net Promoter Score (NPS)** — "¿Qué tan probable es que recomiendes este producto?" (0-10)

- Promoters (9-10) - Passives (7-8) - Detractors (0-6)
- NPS = % Promoters - % Detractors

## PIVOT O PERSEVERAR — LA DECISIÓN CENTRAL

"A pivot is a structured course correction designed to test a new fundamental hypothesis about the product, business model, or engine of growth."

**NO es abandonar. Es cambiar la estrategia manteniendo la visión.**

### Los 10 tipos de Pivot

| Tipo                  | Descripción                                                |
| --------------------- | ---------------------------------------------------------- |
| Zoom-in               | Una feature se convierte en todo el producto               |
| Zoom-out              | El producto se convierte en una feature de algo más grande |
| Customer Segment      | Mismo producto, diferente cliente                          |
| Customer Need         | Mismo cliente, diferente problema a resolver               |
| Platform              | De app a plataforma (o viceversa)                          |
| Business Architecture | De high-margin/low-volume a low-margin/high-volume         |
| Value Capture         | Cambio en modelo de monetización                           |
| Engine of Growth      | De viral a sticky a paid (o combinación diferente)         |
| Channel               | Mismo producto, diferente canal de distribución            |
| Technology            | Mismo resultado, diferente tecnología                      |

**Cuándo pivotar**:

- Las medidas de progreso no mejoran a pesar de experimentos
- Cada experimento confirmatorio no tiene un éxito claro
- El equipo pierde la convicción de que el camino actual llegará al objetivo

**Cuándo perseverar**:

- Los experimentos revelan señales positivas aunque el crecimiento sea lento
- El aprendizaje está acumulando y el equipo sabe por qué las cosas funcionan o no

## LOS 3 MOTORES DE CRECIMIENTO

### Motor 1 — STICKY (Retención)

**Funciona cuando**: El negocio retiene a los clientes que adquiere.

**Métrica clave**: Churn Rate vs Acquisition Rate

- Si Churn < Acquisition → creces
- Si Churn > Acquisition → mueres aunque adquieras muchos clientes nuevos

**Ejemplo**: Servicios de suscripción, apps de hábito, plataformas con switching costs.

### Motor 2 — VIRAL

**Funciona cuando**: Cada usuario trae nuevos usuarios como producto del uso normal.

**Métrica clave**: Viral Coefficient (k)

- k > 1 → crecimiento explosivo
- k < 1 → crecimiento limitado aunque sea positivo

**k = # de invitaciones enviadas × tasa de conversión de invitación**

Ejemplo: Facebook (cada perfil = invitación implícita), WhatsApp (necesitas convencer al receptor de instalar).

### Motor 3 — PAID

**Funciona cuando**: El costo de adquirir un cliente (CAC) es menor que el valor de vida del cliente (LTV).

**Métrica clave**: LTV / CAC > 3 (regla general saludable)

**Escalabilidad**: Si LTV/CAC > 3, puedes gastar más en adquisición → crecimiento predecible.

## INNOVATION ACCOUNTING (3 pasos)

1. **Establecer baseline con MVP**: ¿Cuál es el estado real actual del negocio (no proyecciones)? Usar MVP para medir datos reales del comportamiento del cliente.

2. **Tunear el motor**: Experimentos para mejorar métricas desde la baseline hacia el ideal. Si los experimentos no mueven las métricas → señal de problema sistémico.

3. **Pivotar o perseverar**: Si las mejoras no se materializan después de razonable esfuerzo → tiempo de pivotar. Retardar el pivote consume el "runway" (tiempo + dinero) sin aprendizaje proporcional.

---

## SMALL BATCHES vs LARGE BATCHES

**Paradoja del lote pequeño**: Intuitivamente parece que hacer las cosas en lote grande es más eficiente. En la práctica, lotes pequeños generan aprendizaje más rápido.

**Ejemplo del folleto**: Doblar y meter 100 folletos en sobres.

- Batch grande: doblar 100 → meter 100 → (si hay error, 100 deshechos)
- Batch pequeño: doblar 1 → meter 1 → (si hay error, solo 1 deshecho, se detecta inmediatamente)

**Aplicación en contenido/producto**:

- Lanzar features pequeñas frecuentemente > esperar release grande
- Publicar contenido frecuentemente en formato mínimo > esperar el contenido "perfecto"
- Testear copy/diseño en pequeños grupos > lanzar a toda la audiencia de una vez

## THE 5 WHYS (Raíz del problema)

Para cada problema observado, preguntar "¿Por qué?" cinco veces:

**Ejemplo**:

1. ¿Por qué el servidor cayó? → Porque un nuevo deploy tenía un bug
2. ¿Por qué llegó ese bug a producción? → Porque los tests no lo detectaron
3. ¿Por qué los tests no lo detectaron? → Porque no había tests para esa función
4. ¿Por qué no había tests? → Porque el equipo tenía prisa y los saltó
5. ¿Por qué el equipo tenía tanta prisa? → Porque el proceso de estimación no incluye tiempo de testing

**Solución**: Implementar tiempo de testing en las estimaciones + regla de no deploy sin tests.

La regla 5 Whys previene "Quick fixes" que no resuelven el problema raíz y reaparecen en otras formas.

---

## ANTI-PATTERNS LEAN STARTUP

- ❌ Planear como si fuera un cohete (plan detallado en condiciones de extrema incertidumbre)
- ❌ "Achieved failure" — ejecutar perfectamente un plan que resultó ser completamente equivocado
- ❌ Vanity metrics que siempre mejoran sin importar qué hagas
- ❌ MVP = producto completo con menos features (en vez de experimento mínimo de aprendizaje)
- ❌ Pivotar demasiado rápido (sin datos suficientes) o demasiado tarde (negándose al aprendizaje)
- ❌ Medir output (features lanzadas, código escrito) en vez de outcomes (comportamiento del cliente)
- ❌ Construir en secreto durante meses antes de mostrar al cliente
- ❌ Escalar antes de tener Product-Market Fit

## PROMPT DE ACTIVACIÓN PARA AGENTES

```
"Apply Lean Startup framework:
BUILD-MEASURE-LEARN: What's the fastest way to test the core assumption right now?
  Design the minimum experiment (MVP) that validates or refutes the most critical hypothesis.
  Don't build features — build experiments.
VALIDATED LEARNING: What data will we look at to know if this worked?
  Define metrics BEFORE launching. Vanity metrics don't count.
  Use cohort analysis, conversion funnels, NPS — not total counts.
PIVOT OR PERSEVERE: Are the metrics moving despite our experiments?
  If metrics don't respond to experiments → systemic problem → pivot signal.
  If metrics respond but growth is slow → still valid → persevere.
ENGINE OF GROWTH: Which engine is this product's primary growth driver?
  Sticky (retention), Viral (k-factor), or Paid (LTV/CAC > 3)?
  Optimize for the engine, not for general growth.
SMALL BATCHES: Ship small, measure, iterate. Never spend months building in secret.
  Each small launch = one cycle of learning. Faster cycles = faster to product-market fit.
5 WHYS: For any recurring problem, trace back to systemic root cause.
  Quick fixes that don't address root cause will resurface.
ANTI-PATTERNS:
  ❌ Rocket-ship planning (detailed plan under extreme uncertainty)
  ❌ Vanity metrics (total users, total downloads — not cohort behavior)
  ❌ Building in secret for months before showing customers
  ❌ Scaling before product-market fit"
```
